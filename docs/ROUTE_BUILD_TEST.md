# Проверка сборки маршрута в новом чате

Общий HTML-шаблон с новой компоновкой дня уже в `main`: [PR #11](https://github.com/WorkKroG/travel-planner-skill/pull/11), merge commit `58c20e55fa46307f1b5fa09f96dd7a79f25795d9`. Это инструкция для ручного сквозного теста. Она не заменяет [runtime workflow skill](../skills/travel-planner/SKILL.md) и не является отчётом о пройденной проверке.

## Подготовка

1. Выберите актуальную копию Travel Planner. Для исходников используйте `main`, содержащий PR #11, и настройку Python 3.12 из [README](../README.md#get-the-source-and-validate-it-locally). Не сбрасывайте рабочую ветку с собственными изменениями ради теста.
2. Если проверяете установленный plugin, убедитесь, что его skill, семь references и HTML assets соответствуют этой версии. По [документации OpenAI](https://developers.openai.com/plugins/build/plugins#how-local-marketplaces-work), локальная установка загружается из кэша; обновление Git не обновляет проверяемую копию само по себе. При старом содержимом сначала обновите установку из актуального локального источника через управление plugins.
3. Откройте новый чат Codex с Travel Planner. Если работаете непосредственно с исходниками, явно укажите путь к `skills/travel-planner/SKILL.md` выбранного checkout. Это проверяет workflow из исходников, но не установку plugin.
4. Для новой поездки выберите отдельную папку вне исходников и установочного кэша. Согласуйте точный путь, название и `trip_id` до `init`. Уже указанные вами значения не нужно подтверждать второй раз. Не используйте `examples/japan-autumn-2026` как рабочую поездку.

## Стартовый запрос

Можно вставить следующий текст и добавить уже известные даты, направление, состав группы и ограничения. Путь, название и ID можно выбрать в разговоре.

```text
Давай соберём мой маршрут с Travel Planner. Веди меня по workflow skill:
собери бриф, исследуй варианты, помоги выбрать маршрут и детализируй дни.
Используй уже сообщённые сведения и спрашивай только недостающее.
До создания файлов согласуем отдельную папку поездки, её название и trip_id.

Веди документы и итоговый маршрут по-русски. Сохраняй решения в канонических
файлах, неизвестные значения и открытые вопросы оставляй явными.
Когда маршрут будет готов к просмотру, выполни доступные проверки и собери
HTML общим шаблоном с жёлтыми шапками дней, фотографиями при наличии,
сценариями и хронологией. Покажи файл и объясни, что ещё требует проверки.
```

## Что должно получиться

Планирование проходит от брифа и исследования к осмысленным вариантам маршрута, выбранным базам и полным дням. Решения сохраняются в `decisions.md`. Часы, цены, транспорт и условия проверяются по актуальным источникам в рамках [правил исследования](../skills/travel-planner/references/research.md); недоступные сведения не подменяются догадками.

В папке поездки остаются пять канонических файлов: `brief.yaml`, `candidates.yaml`, `itinerary.yaml`, `readiness.yaml`, `decisions.md`. Если используются фотографии, сохраняются также файлы `media/` и их источник, авторство, лицензия, alt и подписи. `sources.md` и `outputs/` пересобираются из этих данных.

После успешных доступных проверок создаётся `outputs/itinerary.html`. В Codex помощник использует `check` и `render` из проверенной установки; `render --at` получает время сборки, а не фиксированное время демонстрационной Японии. Этот параметр не проверяет внешние источники и не пересчитывает их свежесть. Успешный `check` подтверждает согласованность записанных данных, а не реальную выполнимость путешествия. Draft / Prepared copy и статус проверки остаются отдельными понятиями.

В HTML проверьте несколько разных дней: обычный, с переездом и с альтернативным сценарием. В шапке должны быть название, дата, номер и три факта; при наличии — до трёх фотографий. Хронология сохраняет все события; утро, день и вечер появляются только при записанных `period`. Внизу дня доступны источники и авторство. На узком экране текст и управление остаются читаемыми. Полные ручные проверки интерфейса и печати перечислены в [release checklist](RELEASE_CHECKLIST.md).

## Продолжение в другом чате

Укажите точный путь к существующей поездке или однозначный `trip_id` и попросите продолжить работу по сохранённым файлам. Не запускайте `init` заново. При переносе на другую поверхность передайте пять канонических файлов и все используемые `media/`; одного HTML достаточно для просмотра, но недостаточно для продолжения редактирования. На поверхности без helpers нельзя заявлять `codex_validated`.

## Как записать результат

Сохраните краткую заметку: дата, поверхность, проверяемый commit или путь установленной копии, папка поездки, исходный запрос и полученный HTML. Для сбоя укажите шаг, ожидаемое и фактическое поведение, текст ошибки или проблемный фрагмент. Отдельно отметьте, выполнялись ли `check`/`render` и что вы действительно просмотрели в браузере. Результаты автоматических тестов репозитория не заменяют этот пользовательский тест.
