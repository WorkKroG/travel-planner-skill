# Проверка сборки маршрута в новом чате

Это инструкция ручного сквозного теста, а не отчёт о его прохождении; runtime workflow принадлежит [skill](../skills/travel-planner/SKILL.md). Состояние слитых изменений и текущей ветки записано в [статусе проекта](PROJECT_STATUS.md).

## Подготовка

1. Выберите актуальный `main` либо конкретную ветку PR, который проверяете, и запишите commit. Выполните настройку Python 3.12 из [README](../README.md#get-the-source-and-validate-it-locally). Не сбрасывайте рабочую ветку с собственными изменениями ради теста.
2. Если проверяете установленный plugin, убедитесь, что его skill, семь references и HTML assets соответствуют этой версии. По [документации OpenAI](https://developers.openai.com/plugins/build/plugins#how-local-marketplaces-work), локальная установка загружается из кэша; обновление Git не обновляет проверяемую копию само по себе. При старом содержимом сначала обновите установку из актуального локального источника через управление plugins.
3. Откройте новый чат Codex с Travel Planner. Если работаете непосредственно с исходниками, явно укажите путь к `skills/travel-planner/SKILL.md` выбранного checkout. Это проверяет workflow из исходников, но не установку plugin.
4. Для новой поездки укажите отдельную папку вне исходников и установочного кэша либо явно поручите выбрать её внутри указанного проекта. Уточнение нужно только для неясного или конфликтующего расположения. Если название и `trip_id` не заданы, помощник выбирает их сам и продолжает без вопроса о подтверждении. Не используйте `examples/japan-autumn-2026` как рабочую поездку.

## Стартовый запрос

Можно вставить следующий текст и добавить уже известные даты, направление, состав группы и ограничения. Папку можно выбрать в разговоре; название и ID помощник может определить сам.

```text
Давай соберём мой маршрут с Travel Planner. Веди меня по workflow skill:
собери бриф, исследуй варианты, помоги выбрать маршрут и детализируй дни.
Используй уже сообщённые сведения и спрашивай только недостающее.
Если папка поездки ещё не определена, уточни её до создания файлов.
Название и trip_id выбери по известным вводным, если я их не задал.

Веди документы и итоговый маршрут по-русски. Сохраняй решения в канонических
файлах, неизвестные значения и открытые вопросы оставляй явными.
Когда маршрут будет готов к просмотру, выполни доступные проверки и собери
HTML общим шаблоном с жёлтыми шапками дней, фотографиями при наличии,
сценариями и хронологией. Покажи файл и объясни, что ещё требует проверки.
```

## Что должно получиться

Планирование проходит от брифа и исследования к осмысленным вариантам маршрута, выбранным базам и полным дням. Решения сохраняются в `decisions.md`. Часы, цены, транспорт и условия проверяются по актуальным источникам в рамках [правил исследования](../skills/travel-planner/references/research.md); недоступные сведения не подменяются догадками.

Для проверки происхождения данных сообщите известный вам факт без ссылки, например об оплате отеля, и отдельную оценку длительности переезда. Помощник должен сохранить первый как `reported` с атрибуцией пользователю, вторую — как оценку с её основанием. В HTML должны остаться эти пояснения, неизвестные суммы и условия. Нельзя выдумывать URL разговора, требовать документы только ради заполнения источников или выдавать оценку за проверенное расписание.

В папке поездки остаются пять канонических файлов: `brief.yaml`, `candidates.yaml`, `itinerary.yaml`, `readiness.yaml`, `decisions.md`. Если используются фотографии, сохраняются также файлы `media/` и их источник, авторство, лицензия, alt и подписи. HTML пересобирается из этих данных. История исследования и обсуждения остаётся в чате; отдельные перечни источников не создаются.

Для дня со сменой отеля и прогулкой сначала оставьте сведения о багаже неизвестными. Помощник должен спросить количество и примерный размер вещей, сохранив условный черновик. Затем сообщите вводные и проверьте всю цепочку в HTML: выселение, сдача/отправка, программа, получение, заселение. Ранний приём вещей не должен превращаться в обещание раннего номера. У основного варианта и резерва должны быть место и окно получения либо явный вопрос, крюк и время на обслуживание; доставка через несколько ночёвок учитывает вещи до получения. Повторите с небольшим рюкзаком, который участник готов носить: ненужное хранение не требуется. Проверьте также альтернативный сценарий и последний день с получением вещей перед аэропортом. Схема и `check` не оценивают выполнимость этой цепочки.

После успешных доступных проверок создаётся `outputs/itinerary.html`. В Codex помощник использует `check` и `render` из проверенной установки; `render --at` получает время сборки, а не фиксированное время демонстрационной Японии. Этот параметр не проверяет внешние источники и не пересчитывает их свежесть. Успешный `check` подтверждает согласованность записанных данных, а не реальную выполнимость путешествия. Draft / Prepared copy и статус проверки остаются отдельными понятиями.

В HTML проверьте несколько разных дней: обычный, с переездом и с альтернативным сценарием. В шапке должны быть название, дата, номер и три факта; при наличии — до трёх фотографий. Хронология сохраняет все события; утро, день и вечер появляются только при записанных `period`. У каждого конкретного основного пункта есть ссылки на официальный сайт и карту/маршрут, в том числе в запасных сценариях. Под фото остаётся короткое авторство; списков источников в HTML нет. На узком экране текст и управление остаются читаемыми. Полные ручные проверки интерфейса и печати перечислены в [release checklist](RELEASE_CHECKLIST.md).

## Обстановка и визы

В разделе подготовки должны быть отдельные пункты «Обстановка и безопасность» и «Визы, въезд и транзит». При выборе маршрута и перед выдачей помощник проверяет актуальные официальные сведения и их применимость к участникам, датам и пересадкам. Для проверки неполного брифа оставьте гражданство или транзит неизвестными: помощник должен уточнить их, а в быстром черновике сохранить явный пробел, не заявляя «виза не нужна». Для недоступного источника ожидается открытое действие, а не подтверждение безопасности.

У каждого пункта проверьте вывод/неизвестность, фактическую дату проверки или «Не проверено», официальные ссылки и явное «Обязательно перепроверить» с условиями и сроками. Напоминание сохраняется после завершённой проверки и видно в печати и без JavaScript. Обновление HTML или успешный `check` не должно обновлять дату фактической проверки либо означать мониторинг обстановки.

## История подбора

Убедитесь, что первая и повторная сборки создают только выбранный HTML, без `sources.md`, каталогов источников и дополнительных перечней. Спросите, почему выбрано одно из мест: ответ должен опираться на доступную историю обсуждения. Если предыдущий чат недоступен, помощник должен сказать об этом и не обещать восстановить историю по версии HTML.

## Продолжение в другом чате

Укажите точный путь к существующей поездке или однозначный `trip_id` и попросите продолжить работу по сохранённым файлам. Не запускайте `init` заново. При переносе на другую поверхность передайте пять канонических файлов и все используемые `media/`; одного HTML достаточно для просмотра, но недостаточно для продолжения редактирования. На поверхности без helpers нельзя заявлять `codex_validated`.

## Как записать результат

Сохраните краткую заметку: дата, поверхность, проверяемый commit или путь установленной копии, папка поездки, исходный запрос и полученный HTML. Для сбоя укажите шаг, ожидаемое и фактическое поведение, текст ошибки или проблемный фрагмент. Отдельно отметьте, выполнялись ли `check`/`render` и что вы действительно просмотрели в браузере. Результаты автоматических тестов репозитория не заменяют этот пользовательский тест.
